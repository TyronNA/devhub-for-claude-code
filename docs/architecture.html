build principles

A project is just a path

A repo registered in Dev Hub does not become a workspace folder. Each chat spawns (or reattaches to) an agent CLI with that path as its cwd. The extension owns lifecycle, transcripts, permissions and presentation; it does not own the agent's intelligence.

All wiring lives in one file. It builds the stores, providers, manager, tree, panel and — only when needed — the HTTP server, then connects them with callbacks, not a DI container. Components take closures rather than references, because “built before or after” and “who is showing this session” are two different questions.

seam A
AgentProvider

Adding an agent CLI means adding one file

interface AgentProvider {
  readonly id: ProviderId;
  isAvailable(): Promise<boolean>;
  start(input): Promise<ProviderTurnHandle>;
  resume(input): Promise<ProviderTurnHandle>;
  discoverHistory(projects): Promise<DevHubSession[]>;
  loadTranscript(session): Promise<DevHubEvent[]>;
}

interface ProviderTurnHandle {
  events: AsyncIterable<DevHubEvent>;   // the whole contract of a turn
  cancel(): Promise<void>;
  getNativeSessionId(): string | undefined;
}

Everything above the providers speaks DevHubEvent and nothing else. The manager, tree and renderer don't know whether a process or a network is underneath.

Proof the seam is real: the third provider spawns no process — it speaks HTTP to a background daemon. The interface never promised a subprocess, only an AsyncIterable, so all three front-ends reuse it unchanged.

session identity

Three backends, three kinds of id ownership

BackendWho mints the idConsequence
CLI ADev Hub mints it and passes it as a command-line flag the id is known before the first output byte
CLI Bthe CLI mints it and reveals it mid-stream the session starts under a temporary pending: key; when the real id arrives the manager rekeys the store, the event cache and the open tab in one step
Daemonthe daemon mints it; the id is its conversation the same id on two daemons is two different conversations, so the session carries the endpoint and the store key is scoped by it

This is exactly the asymmetry most abstractions try to hide and then leak. Here it is named: one rekey path, one scoping rule, both tested.

concurrency

A claim, not a counter

A plain count is wrong, because start() has several awaits inside — probing the CLI, spawning — before anything lands in the active map. N turns slip through together.

reserveSlot()
reserves before the awaits, releases in finally. This is the global cap.
claim(session)
a per-session lock, so two resumes never overlap on one thread.
isBusy()
the only correct question for “can I send yet?”

cancel() writes the cancelled status immediately, while the consume loop only clears the active entry after draining the stream. In between, the status says idle while the session is not. Reading the status to decide whether to send a new turn is writing a bug.

Out-of-turn operations — compacting context, which can take a minute — use their own lock: they hold the session but deliberately do not take a slot, because compaction is not a turn.

front-end

Two hosts, one renderer

The phone is not a mirrored webview. A VS Code webview is an iframe served from a CDN origin with a service worker, and Safari on iPhone can't run it. So the same renderer script is served as a real HTTP page over a different pipe: SSE down, POST up, identical protocol. The mobile protocol may only add messages on top of the panel protocol; the shared validator is never loosened.

The price of one renderer is a standing rule: a behaviour change in one host almost always needs the same change in the other.

Constraints shared by both hosts

  • The DOM is built with createElement, no innerHTML anywhere. Agent output is untrusted markup.
  • The panel runs under default-src 'none' with a nonce; the HTTP page carries an equivalent 'self' policy, opening data: only for images because a pasted image in a transcript may be just a data URI.
  • Image serving is limited to exactly two folders.
  • The script runs in the viewer's browser, so no syntax newer than old WebKit. A test greps the shipped file to enforce it.

permission contract

A waiting CLI must never be left hanging

When the agent asks “may I run this?”, it stands still until it gets an answer.

Every permission request gets an answer. Tab closed, panel disposed, turn ended or timed out — all of them deny.

The routing order is deliberate. The phone is asked first: it only accepts when a client really holds that session, and the person holding the phone can't see the desktop panel to approve. Then the panel. Then a notification, and only when that session isn't the one open on screen.

storage

Three JSON files, no database

Atomic writes: to a temp file, then rename. No indexes, no migration engine.

  • workspaces.json — logical workspaces to project paths, normalised through realpath and lowercased on case-insensitive filesystems.
  • sessions.json — session rows: provider, native id, project, title, status, usage.
  • queues.json — prompts typed but never sent. Restored by handing the text back to the user, never re-queued: a queue from a window closed three days ago running by itself is not a feature.

Session content is not duplicated. The agent CLIs already write their own transcripts to disk, so a provider finds and parses those, and a reconciler merges what it found with what the store already knows.

beyond chat

Two things share the tree but not the providers

  • Background bots — registered as a folder plus four verbs (start, stop, status, logs; make by default), run with a timeout. Status is read by parsing output. Some bots also expose task rows over their own loopback API, read in read-only mode.
  • Listening ports — scans the user's own listening sockets, grouped by owning project via each process's cwd, else by owning bot, then the pinned list. No root, so it only sees your own processes — exactly the scope it needs.
